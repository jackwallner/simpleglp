# Simple GLP — UX Improvement Suggestions (c521)

This document suggests product and UX improvements for **Simple GLP**, grounded in how someone actually uses the app: weekly injection, occasional catch-up logging, optional detail entry, checking “am I on track?”, and glancing at patterns over months. Each item ties a **user situation** to a **suggested change**. Nothing here is implemented — it is analysis only.

---

## How people use Simple GLP today (from the codebase)

The app is built around a single recurring action: **tap “I took my shot”** on Home (or the widget / watch). Everything else is secondary:

| User intent | Where it lives today |
|-------------|----------------------|
| Log right now | Home big button, widget `LogShotIntent`, watch button |
| Fix time/dose after the fact | **Optional** tab → `EditEventSheet`, or History → same sheet |
| See what’s next | Home “Next shot” card (`ScheduleEngine`) |
| Plan titration ahead | Settings → Dose schedule (`DoseScheduleView`) |
| See adherence / timing | Patterns tab (`InsightsView`) — text cards only |
| Backup data | Settings → Export / Import (wired to services) |
| Pro alerts | Patterns or Settings → paywall → `ProAlertsConfigView` |

Health metrics are **captured on every shot** (`HealthKitService` → `ShotEvent`) but **never shown** in any screen. That gap is the largest missed UX opportunity.

## 1. First run and setup

### A. Explain notifications before the system sheet appears

**User situation:** During onboarding they turn on “Remind me on shot day,” finish setup, and assume reminders work. The actual iOS permission dialog is deferred until `ReminderService.scheduleNextShotReminder` runs — which can feel like the toggle lied if they tapped “Don’t Allow.”

**Suggested change:** Add a short onboarding step (or inline card on the reminder step): what the notification says, that it fires on shot day with optional lead time, and a “Enable reminders” button that *then* calls `UNUserNotificationCenter.requestAuthorization`. If denied, show a one-line path: Settings → Notifications → Simple GLP.

### B. Health permission priming (beyond a toggle)

**User situation:** On the last onboarding step they see “Auto-capture Health context” with footnote copy, then iOS may immediately show the Health access sheet. Many users deny without reading.

**Suggested change:** A dedicated screen before the system dialog: bullet list of what is read (weight, steps, sleep, etc.) and that **nothing is uploaded** — it attaches to the shot record on device. “Continue” triggers `prepareAuthorizationDuringOnboarding`. If they skip, don’t block finish; show in Settings how to turn it on later.

### C. Introduce dose titration during onboarding, not only in Settings

**User situation:** Someone starting Wegovy at 0.25 mg knows they’ll step up monthly. They complete onboarding with one static dose, then must discover Settings → Dose schedule to plan escalations.

**Suggested change:** After medication + current dose, optional step: “Planning dose increases?” with medication-specific presets (already in `GLPMedication.standardDoseStepsMg`) and suggested start dates (e.g. +4 weeks). Skippable. Reduces “I forgot to bump my dose in the app” and mismatched logs after titration day.

### D. Align plan editing with onboarding dose UX

**User situation:** Onboarding uses dose **pickers** for branded meds; Settings → Medication & schedule (`PlanEditorView`) still uses a free-text mg field. Editing the plan feels like a different, harder app.

**Suggested change:** Reuse the same preset picker + “custom dose” pattern from `OnboardingView.doseField` in `PlanEditorView`.

### E. Clarify “start date” vs “day of week”

**User situation:** On the schedule step they set both a calendar start date and a weekday segment. It’s unclear which drives the first reminder and adherence window.

**Suggested change:** One sentence of helper copy, e.g. “Your shot day is every Tuesday; start date is when you began this schedule.” Consider defaulting weekday from start date when they pick a date.

## 2. Logging a shot (core loop)

### A. First-class “I took it yesterday” without logging a wrong time first

**User situation:** They inject Tuesday morning but open the app Wednesday night. Tapping Home logs **now**, shows “A little late,” and they must hunt Optional/History to fix the timestamp.

**Suggested change:** On Home, secondary action: “Different time” or long-press on the big button → lightweight sheet (date + optional time, defaults to last expected shot day). `ShotCaptureCoordinator.captureShot` already accepts `tapDate`; Home never exposes it. Keeps the one-tap default while honoring real behavior.

### B. Make recent shots on Home tappable

**User situation:** Home lists “Last few shots” as read-only rows. To correct the latest entry they switch tabs.

**Suggested change:** Tap row → `EditEventSheet` (same as Log Hub / History). Keeps correction on the tab they already use most.

### C. Injection site rotation at log time

**User situation:** Rotating abdomen / thighs / arms reduces irritation. Today site is only in Optional details, usually empty unless they open a sheet after logging.

**Suggested change:** Small “Site” chip row on Home (last site + suggested next in rotation). Pass selection into `captureShot` or pre-fill the new event. Optional: simple body diagram instead of text-only `InjectionSite` picker.

### D. Wire up “Prompt for details after shot”

**User situation:** Settings has “Prompt for details after shot” (`promptForDetails`) but nothing reads that flag — users enable it and nothing happens.

**Suggested change:** After successful capture, if enabled, present `EditEventSheet` for the new event (or navigate to Optional with sheet open). Delivers on the setting’s promise without breaking one-tap for users who leave it off.

### E. Stronger feedback when logging from widget or watch

**User situation:** Widget logs via app group, opens app, ingests on `scenePhase == .active`. Undo exists on Home (`showUndoOption`) but only if they land on Home and notice the banner.

**Suggested change:** On ingest from widget/watch, brief full-width confirmation with **Undo** and “Add details” — same session, don’t rely on a subtle `bannerMessage` alone. Watch: mirror undo or “Open on iPhone to edit” when phone unreachable.

### F. Overdue and “due today” states on Home

**User situation:** “Next shot” shows a future date/time but not “Due today,” “Overdue by 1 day,” or countdown. After a missed week they must infer from adherence labels in History.

**Suggested change:** Derive copy from `ScheduleEngine.nextExpectedDate` vs `Date.now` (and last logged shot). Plain language reduces anxiety and explains why a log might count as late.

## 3. Optional details and symptom tracking

### A. Rename and orient the “Optional” tab

**User situation:** Tab label “Optional” (`RootTabView`) doesn’t say what to do. Footer says “Quick add details” but the nav title is “Optional details.”

**Suggested change:** Title like “Shot details” or “How you felt”; tab label “Details.” Lead with the most recent shot and a single CTA: “Add details to latest shot.”

### B. Replace symptom steppers with faster, human scales

**User situation:** Nausea, appetite, food noise, wellbeing use 0–5 **Steppers** in `EditEventSheet` — many taps, feels clinical.

**Suggested change:** Segmented labels (None / Mild / Moderate / Severe) or horizontal chips. Consider GLP-1-relevant additions: fatigue, constipation, reflux — still optional, still private.

### C. Show captured health context when reviewing a shot

**User situation:** They enabled Health capture; after logging they have no in-app proof it worked. Data sits on `ShotEvent` fields never rendered in views.

**Suggested change:** In `EditEventSheet` or History detail: read-only section “That day” — weight, steps, sleep, protein if present; if pending/failed, show `healthStatusMessage` and retry. Builds trust and explains partial capture.

### D. End-of-day refresh for “today” metrics

**User situation:** Logging at 9 AM stores steps/protein **as of 9 AM** (`captureSnapshot(at: timestamp)`). Their “shot day” story is incomplete.

**Suggested change:** `enrichPendingCapturesIfNeeded` already revisits pending health rows — extend with end-of-day job or next-open sync to refresh same-calendar-day aggregates so Insights and detail views aren’t morning-only snapshots.

## 4. History and long-term record

### A. Richer history rows without opening every shot

**User situation:** History shows date, time, dose, schedule pill. Injection site, symptoms, and health snapshot are invisible until tap.

**Suggested change:** Subtitle line: site + top symptom, or icons when data exists. Helps “which thigh was last week?” without drilling in.

### B. Confirm destructive delete

**User situation:** Swipe-to-delete in `HistoryView` is immediate — easy to lose weeks of context by mistake.

**Suggested change:** Confirmation alert or undo toast after delete.

### C. Surface export as “your data, your phone”

**User situation:** Export works (`ExportView` + `ShareLink`) but lives deep in Settings. Users switching phones or seeing a clinician may not find it.

**Suggested change:** One line under History footer: “Backup or share CSV” → Export. Reinforces privacy story from README.

## 5. Patterns, insights, and Pro value

### A. Visualize what you already collect (highest impact)

**User situation:** They use GLP-1 for months and want to see weight trend vs dose, or whether nausea clusters after injection. Patterns tab only shows adherence % and “most shots on Tuesday” after enough samples.

**Suggested change:** Swift Charts in Patterns: weight over time with vertical markers at shot dates/doses; toggles for glucose, sleep, steps. Uses existing `ShotEvent` fields — no new data collection.

### B. Symptom cycle relative to shot day

**User situation:** Side effects often peak day 1–2; appetite returns toward day 6–7. Numeric logs in the sheet don’t reveal that rhythm.

**Suggested change:** Chart symptoms by **days since last shot** (Day 0, +1, +2…) aggregated across history. Copy like “Your nausea often peaks the day after a shot.”

### C. Progress toward insights, not a dead end

**User situation:** With fewer than 5 shots, Patterns shows only “Keep logging…” (`minimumSampleSize`). No progress bar or “3 of 5.”

**Suggested change:** “2 more shots until adherence insights” with optional preview of what unlocks (and what Pro adds).

### D. Make Pro benefits tangible before paywall

**User situation:** Free users see adherence + weekday pattern; Pro promises “pattern alerts” but paywall is a short list of packages (`SimplePaywallView`).

**Suggested change:** Feature comparison: proactive alerts, quiet hours, pattern sensitivity, future charts. Use `RevenueCatUI` paywall or branded layout consistent with `AppTheme`. Show **example** alert copy so they understand what they’re buying.

### E. Connect Patterns to Settings dose schedule

**User situation:** They scheduled a titration step; Home shows new dose on the right date, but Patterns doesn’t annotate dose changes on the timeline.

**Suggested change:** Mark dose step boundaries on charts and a one-line “Dose increased to X on [date]” in history/insights.

## 6. Settings, reminders, and trust

### A. HealthKit status and re-enable path

**User situation:** They denied Health access or use a new phone. No in-app status or “Open Health” deep link.

**Suggested change:** Settings section: Connected / Limited / Off, with steps to fix in Health app. Optional “Refresh context for last shot.”

### B. Reminder preview and test

**User situation:** Lead time is a stepper in minutes; they’re unsure when the notification will fire.

**Suggested change:** “Next reminder: Tuesday 8:45 AM (15 min before shot)” computed from plan + `ReminderService`. Mirror Pro’s “Send test alert” for shot-day reminders.

### C. Explain schedule labels in user language

**User situation:** Pills say “On schedule,” “A little late,” “Manual,” “Not mapped” (`ScheduleMatchStatus`) without explaining the ±18h on-schedule window (`ScheduleEngine.onScheduleWindow`).

**Suggested change:** Info affordance on first late/on-time label, or Settings → “How we count on schedule” in plain language (not medical advice).

### D. Medical disclaimer where decisions happen

**User situation:** Disclaimer only in Settings → About. Someone might treat adherence % as clinical guidance.

**Suggested change:** Subtle footer on Patterns and plan editors: tracking tool only; follow prescriber instructions.

## 7. Widget, Watch, and cross-device

### A. Widget: accidental tap vs speed

**User situation:** Home Screen widget is one tap, no hold-to-confirm (`LogShotIntent`). Fast when intentional; risky when scrolling past widgets.

**Suggested change:** Optional widget configuration: “Require confirmation” for medium widget; or haptic + 3s undo banner when app opens (see §2.E).

### B. Watch: parity and reassurance

**User situation:** Watch logs via `WatchConnectivityController`; user sees “Logged” on wrist but may not know if iPhone synced.

**Suggested change:** Clear sync states: “Saved on iPhone” / “Will sync when phone is nearby.” No undo on watch today — at minimum don’t show success until ack from phone when possible.

### C. Reduce duplicate `PhoneWatchSession.start`

**User situation:** Session starts in `AppDelegate` and again in `SimpleGLPRootContent.onAppear`. Unlikely user-visible, but duplicate handlers could confuse debugging of missed watch logs.

**Suggested change:** Single startup path (delegate only) so background watch → phone capture is predictable; document for support: “Open app once after watch log.”

---

## 8. Information architecture

### A. Five tabs vs “one big button” promise

**User situation:** Onboarding says “One big button” and “optional details if you want them,” but the tab bar exposes Home, Optional, History, Patterns, Settings — cognitive load for minimalists.

**Suggested change:** Consider 3 tabs: **Log** (Home + details entry), **Timeline** (history + patterns), **Settings**. Or keep five tabs but default new users to Home with guided first-shot tooltip.

### B. Unify “fix this shot” entry points

**User situation:** Same `EditEventSheet` from Optional and History; Home doesn’t participate. Mental model fragments.

**Suggested change:** One consistent “Edit shot” path from Home recent list, notification tap (future), and History.

## Priority sketch (user impact × leverage)

| Priority | Theme | Why |
|----------|--------|-----|
| P0 | Show Health + symptom data in UI | Data already exists; users think capture is broken |
| P0 | Log past shot / Home → edit | Fixes the most common real-world logging mistake |
| P1 | `promptForDetails` + site at log time | Small code, completes promised behavior |
| P1 | Permission priming (notifications + Health) | Improves reminder and context opt-in |
| P1 | Patterns charts + dose markers | Differentiates app for long-term users |
| P2 | Plan editor dose presets, onboarding titration | Reduces setup errors |
| P2 | Paywall / Pro storytelling | Conversion without changing core free loop |
| P2 | Widget confirm / watch sync copy | Edge cases but high annoyance when wrong |

## What’s already in good shape (don’t regress)

- One-tap capture with async Health enrichment and undo on Home.
- Widget → app group → `ingestPendingWidgetShot` pipeline.
- `EditEventSheet` supports **when** and **dose** with schedule recalculation on timestamp change.
- Onboarding dose **presets** for branded medications.
- Settings **Dose schedule** for titration steps.
- Export CSV + Import file picker (not placeholders).
- `AppDelegate` starts watch session for background capture path.

Improvements above build on these strengths rather than replacing the core “log fast, enrich later” architecture.
