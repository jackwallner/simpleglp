B1

One failed database open makes the whole dose history disappear, with no message and no way back

highplausibledata
Impact

A customer loses their medication history, streak and plan from one transient failure. The data is still on the phone but the app can no longer reach it, and a reinstall deletes it for good.

How it happens
  1. Use the app for months. The plan, every logged dose and the titration steps live only in this one store.
  2. The app starts at a moment the store file cannot be opened. Examples: iOS starts it in the background after a restart, before the phone has been unlocked (a Watch log arriving, app prewarming, a Siri or notification log), or storage is full.
  3. makeContainer uses try?, so every error looks like corruption. The store and its sidecar files are renamed to .corrupt-<uuid> and a new empty store is created (or an in-memory one if that fails too).
  4. On the next open the customer sees onboarding and an empty history. Nothing reads the renamed files again, and nothing tells the customer what happened.
Where
SimpleGLP/Services/GLPModelStore.swift:10SimpleGLP/Services/GLPModelStore.swift:17SimpleGLP/Services/GLPModelStore.swift:60SimpleGLP/Services/DoseIntents.swift:15SimpleGLP/Services/PhoneWatchSession.swift:70
Suggested fix

Move the store aside only for a real corruption or migration error. For any other error keep the file, run this launch on an in-memory stand-in and reopen when protected data becomes available (copy Baby Tracker's approach). If the live store is empty and a .corrupt-* copy exists, offer to restore it.

Evidence
if let container = makeContainer(schema: schema, url: url) {
    return container
}
// A failed migration or half-written file can leave the store unopenable.
// Shot history exists nowhere else, so move it aside instead of deleting it.
quarantineStore(at: url)
...
return try? ModelContainer(for: schema, configurations: [config])

There is no error classification, no retry, no alert and no code that reads a .corrupt-* file. The app has three background entry points that open the store (Watch messages, dose intents, notification actions) and no check for protected data. Baby Tracker already treats this as real: its Persistence.swift moves a store aside only when the error is a corruption error, and otherwise runs on a stand-in until protectedDataDidBecomeAvailable fires.

Checked by: Code read by Claude Fable; same pattern found in Sober.

Not proven: Not reproduced on a device. Unproven: that iOS starts this app before first unlock, and that the rename succeeds then. A disk-full or migration failure reaches the same code without that condition.

B11

Every-N-days plans (not daily, not weekly) move their dose to another day when the phone changes time zone

lowconfirmededge
Impact

The stored first dose is an instant (Wednesday 01:00 in New York). The schedule takes the local calendar day of that instant, so the dose day becomes Wednesday 22:00, about 21 hours later than the user's own Tuesday night routine, and it flips back on return. Weekly plans avoid this because normalizeScheduleAnchor re-pins their weekday on launch; the guard skips every other cadence. Reminders and the late-dose nudge follow the shifted day. How it happens

  2. Fly to New York (3 hours east) and open the app.
  3. Look at Home and the dose reminders.
